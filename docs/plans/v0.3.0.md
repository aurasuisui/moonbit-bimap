## 1. 背景与真源核验(里程碑 1)

三项核验按审核结论收口(证据为 moon 0.1.20260827 的 core 源码),结论记入 SPEC §:

1. **bimap-rs serde 特性:存在**(docs.rs 自 0.4 起有 `bimap::serde` 模块,0.6.3 仍在)。
   其序列化格式与冲突行为留待 W1 实测记录,仅作 SPEC 对照——本库 from_json 只对齐
   自家 ToJson 格式 `{ "<left>": <right-json>, ... }`,**不对齐 Rust serde 格式**,
   差异在 SPEC §记录裁定。
2. **`@json` 解析保序:定案**。core `Map` 即 LinkedHashMap
   (`builtin/LinkedHashMap.mbt`:"maintains the order of insertion");`json/parse.mbt`
   的 `parse_object` 以 `map[name] = ctx.parse_value(...)` 构造,重复键为赋值覆盖。
   结论:**last wins + 键序保持是核心源码事实**。BiMap 往返后插入序与文本键序一致,
   文档可声明"顺序保持"。W1 补一个冒烟测试确认即可。
   (BiBTreeMap 排序自规范,键序无关,不受影响。)
3. **`Json` 的 trait:定案为"类型级不可行"**。`json/pkg.generated.mbti` 中 Json 仅有
   `Show`/`ToJson`/`FromJson`,无 `Hash`/`Eq`/`Compare`。因此 **R=Json 被
   BiMap 的 `R : Hash + Eq` 与 BiBTreeMap 的 `R : Compare` 在类型层直接排除**,
   文档措辞用"类型级不可行",不写"未实现";往返测试用 R=String/Int。

## 2. API 设计

### 签名(新增文件 `src/json.mbt`,两类型共享错误枚举)

```moonbit
// 错误类型:语法/类型错误与双射冲突统一为单一错误通道
pub enum BiMapDecodeError {
  Decode(@json.JsonDecodeError)            // JSON 语法/类型错误(透传)
  DuplicateRightValue(String, String, String)
  // 双射冲突:(右值渲染, 已占用者左键渲染, 冲突新左键渲染)
} derive(Debug, Eq)

pub fn[R : FromJson + Hash + Eq] BiMap::from_json(
  json : Json,
) -> BiMap[String, R] raise BiMapDecodeError

pub fn[K : Hash + Eq, R : FromJson + Hash + Eq] BiMap::from_json_with(
  json : Json, parse_key : (String) -> K,
) -> BiMap[K, R] raise BiMapDecodeError

pub fn[R : FromJson + Compare] BiBTreeMap::from_json(
  json : Json,
) -> BiBTreeMap[String, R] raise BiMapDecodeError

pub fn[K : Compare, R : FromJson + Compare] BiBTreeMap::from_json_with(
  json : Json, parse_key : (String) -> K,
) -> BiBTreeMap[K, R] raise BiMapDecodeError
```

`BiMapDecodeError` 除 `derive(Debug, Eq)` 外需**手写 `Show`**:稳定文本渲染
(三元组载荷),供错误消息与 Tier 2 golden-file 快照共用,禁止实现时临时发明格式。

### 自由函数(P1-1 裁定)

`lib.mbt` 加两个自由函数 `from_json`/`from_json_with`,**仅覆盖 BiMap**(镜像
indexmap,`@aurasuisui/bimap.from_json(json)` 可直呼)。MoonBit 顶层函数不能按返回
类型区分同名函数,BiMap 与 BiBTreeMap 无法共享同一自由函数名;**BiBTreeMap 一律走
`BiBTreeMap::from_json(...)` 方法调用**,SPEC/README 各写一句。

### 约束(bounds)理由

- BiMap 需要 `R : Hash + Eq`:反向表对右值建哈希,双射不变式使然(与
  `Arbitrary` impl 注释同理)。**这是与 indexmap `from_json` 的唯一 bounds 差异
  (indexmap 只要求 `V : FromJson`),SPEC 与 README 需写明。**
- BiBTreeMap 需要 `R : Compare`:两棵 SortedMap 对右值排序。
- 键侧:字符串键直用 `from_json`;非字符串键走 `from_json_with` 提供 `parse_key`,
  与 indexmap 对齐。

### parse_key 契约(P1-2 裁定)

`parse_key : (String) -> K` 为**全函数**(无 raise 通道,保持 indexmap 对齐)。解析
失败必须在 parse_key 内部消化(如 catch 兜底到默认值);**文档注明"parse_key 必须
total"**。否决备选方案(签名改 `(String) -> K raise ?` 并把错误包进新变体):那会
成为与 indexmap 的第三处差异,徒增 API 面;SPEC 记此裁定。

## 3. 语义裁定(核心设计,逐条记录)

### 3.1 双射冲突 → 严格报错(不静默蒸发)

JSON 对象中两个不同的左键映射到**同一个右值**时(如 `{"a":1,"b":1}`),若沿用
`insert` 语义,第二条会触发 C3 蒸发,旧对**静默丢失**——反序列化不可接受。
**裁定:检测到右值冲突即 raise `DuplicateRightValue`,整次解析失败,不产出半成品。**
错误载荷含右值渲染与**两个冲突左键的渲染**(先已占用者、后新到者),便于定位;
(对照:这是 from_json 与 indexmap 第二个语义差异;indexmap 无此约束,insert 即可。)

### 3.2 重复键 → last wins(跟随 core Map 语义)

- 文本层重复键(`{"a":1,"a":2}`):`@json.from_json` 的 core Map 语义 last wins,
  解析后再校验双射。**注意先 last-wins 再查冲突**:`{"a":1,"b":2,"b":1}`
  last-wins 得 a=1,b=1 → 冲突报错;SPEC 记录此顺序。
- `parse_key` 碰撞(如 `parse_key("1")` 与 `parse_key("01")` 同值):后到者覆盖,
  last wins。**裁定理由(审核 P2):** parse_key 碰撞与文本重复键同构——多个文本键
  解析为同一逻辑键,与同一文本键重复出现等价,跟随 last-wins 保持单一规则,同时
  避免与 indexmap 产生第三处差异;而右值冲突(§3.1)破坏的是**数据结构定义层面的
  双射不变量**并导致已有对蒸发,两者破坏层面不同,故严格性差异是自洽的。SPEC
  记录此裁定,不只写"与 indexmap 一致"。

### 3.3 顺序与往返保证

- 核验 1.2 定案:BiMap 的 `from_json(m.to_json()) == m` 成立(Eq 集合语义),且迭代
  序与 JSON 文本键序一致(core Map 保序),文档声明"顺序保持"。
- BiBTreeMap:`from_json(m.to_json()) == m` 恒成立(排序自规范),输入键序无意义。
- 非字符串键往返需 `parse_key = Show 的逆`,文档给出 Int 键示例(parse_key 内
  catch parse_int 失败)。

### 3.4 与既有收口点的关系(纪律登记)

from_json 是**数据入口,不是 mutation 收口**;内部禁止直接触表,实现路径:
1. `@json.from_json` 解析 → 2. 右值查重(O(n),先于任何插入)→ 3. 全量
   `from_array` 或逐对 `insert_no_overwrite`(无冲突后必成功)。
   查重先行是**实现选择**(避免构造过程中的中间态 C3 蒸发、意图显式),不是正确性
   要求——失败时局部 map 直接丢弃,本无外部副作用(审核修正)。

### 3.5 错误优先级(审核 P2,SPEC 写死)

**值解码先于冲突检测**:若同一对象内既有值类型错误又有右值冲突,报 `Decode`
(先经 `@json.from_json` 解码,R 解码失败时冲突检测无从谈起)。实现与测试不得各猜
各的。

## 4. 测试清单(里程碑 4)

按 RELEASE_CHECKLIST Tier 0–4 落地,新增用例全部进 `src/json_test.mbt`(或按
类型拆 `bimap_json_test.mbt`/`bbtreemap_json_test.mbt`)。

### Tier 0 — API / 单元(每个公开方法按契约逐条)

- `{}` → 空 map;单对;多对(检查 `get_index` 顺序 = 文本键序)。
- R = String / Int / Bool 三种基本值类型。
- `from_json_with` + Int 键(parse_key 为全函数,内部 catch `parse_int` 失败;
  按 P1-2 不设"透传"路径)。
- 文本重复键 last wins;parse_key 碰撞 last wins。
- **双射冲突 → `DuplicateRightValue`**:精确断言载荷三元组(右值、已占用者左键、
  新左键的渲染)。
- 非对象 JSON(`[]`、`"x"`、`1`、`null`)→ `Decode` 透传。
- 值类型不符(右值是数组给 String 槽位)→ `Decode` 透传。
- **错误优先级(§3.5)**:同一对象既有类型错误又有右值冲突 → 报 `Decode`。
- BiBTreeMap:同键不同输入顺序 → 输出一致(排序规范);冲突同样报错;方法调用
  路径 `BiBTreeMap::from_json(...)`(P1-1)。
- bounds 最小化编译测试(进 `generics_test.mbt`):from_json 不要求 K 的 Show;
  BiMap 的 R 必含 Hash+Eq、BiBTreeMap 的 R 必含 Compare(编译期即约束)。

### Tier 1 — 系统化正确性

- **QuickCheck 往返(主测)**:Arbitrary BiMap[String, Int] → to_json → from_json
  → `==` 原图 + 逐位置 `get_index` 一致(保序声明,核验 1.2 已定案)。
- BiBTreeMap[String, Int] 同式往返。
- **模型测试**:手工 JSON 文本 → 解析 → 与朴素 Array 模型比对(冲突文本 → 与
  模型预测的报错一致)。
- **差分/真源**:from_json 是原创扩展(对齐本库 ToJson 格式,不对齐 Rust serde),
  无真源 oracle——按 SPEC 惯例记"无差分 oracle,语义由测试钉死"。

### Tier 2 — 现实边缘

- Unicode 键(emoji/CJK)、空串键、转义键(`a"b\\c`、换行、tab)→ 往返无损。
- **冲突风暴**:多对共享同一右值、last-wins 后新生冲突(3.2 例)、10k+ 对往返
  (压力 + 顺序)。
- **R=Json:类型级不支持**(核验 1.3 定案,Json 无 Hash/Eq/Compare)——文档记录,
  不写测试。
- **golden-file 快照**:锁定 ToJson 输出格式(把 Tier 2 原 ⊘ 项补成 ✅)与
  `DuplicateRightValue` 错误消息格式(三元组载荷;渲染路径用 §2 手写的 `Show`)。

### Tier 3 — 非功能
